# 设计裁决（代码里看不出动机）

本文是 `AGENTS.md`「设计裁决」提纲所指全文，逐字搬运、未作改写。记录的是代码本身看不出、但改动前必须知道的取舍。

- 条目按主题分组，新增请追加到对应分组末尾，不要打散既有顺序。
- 结论与理由已分离：本节写「是什么」，`AGENTS.md` 的提纲只写「结论」。
- 若某条裁决被推翻，就地改写并保留原措辞线索，不要静默删除。

- **配置解析优先级**：当前版本快照 → ≥ 最低支持的最高可解析快照（含更高版本，按当前 schema 降级解析，多余键忽略、`efforts` 宽松保留）→ 内置默认。更高版本快照降级落盘后**永不清理**，供再升级无损回退。当前版本快照非法**或残缺**时按**当前生效值**规范化重写——残缺会被 `parseSnapshot` 补默认判为合法，故须比对规范化结果而非只判非法。
- **`allowUpdate` 含缺失补写**，`autoFill` 关闭也拦不住：语义是"以目录为准同步该字段"。新旧相同则跳过，**数据无档位不删除已有配置**。
- **`force` 是单次绕过**（三项临时为真、不落存储、不重拉目录，避免把网络耗时算进按钮反馈）；与 compat 无关；`fix` 返回值只计模型变更数（记忆清理与 compat 不计入，保持 RPC 反馈契约）。
- **`fix` 读 `descriptor.user`**（原始用户段）：避免规范化形态与写入形态不一致而反复触发重写。写回带 revision 围栏，冲突时重读重算（限次）；写失败先告警再抛出（事件侧吞 rejection，RPC 转 `ok:false`）。
- **空壳字段一律删除，判据只有一处 `stripEmptyFields`**（`reasoningEfforts` 为空对象、`input` 为空数组、`compat` 为空对象；宿主语义等同未声明，删除无损幂等）。**五条写回路径统一过它**——`fix` 填充、`reset` 重置、`restore` 恢复、`prune` 剔除（验证判定出档位不支持后的写回）、`fill` 探测式填充的预声明与收敛（两次写回共用 `planEffortApply`，只调一次），任何一处都不另写一份判据。原先是分叉的：`fix` 只清 `input` + `compat`、`prune` 只清 `reasoningEfforts`，于是空壳既会被当成「已声明」（缺失补写不触发、写入判定反复触发），也会被恢复备份原样带回。表里只列这三个键：用户自定义字段一律保留，空壳是逐键核过的而非「通用空即删」——函数无空壳时返回**原引用**，调用方以引用相等判「这一条无需重建」。两处配套改动：`fix` 的缺失补写按**清理后**的值认（否则 `reasoningEfforts: {}` 既不被填又被清，得等下一轮才补上）；`reset` 的写回触发只看「带没带推理级别」（`Object.hasOwn`），否则带空壳的模型会被算进「重置 N 个模型」而虚高。`compat.ts` 的路由级整段 `unset` 是另一种作用域（不是模型字段清理），不经此函数。
- **compat「开启即添加、关闭即移除」，与模型参数取向相反**（后者关闭只是不写、存量保留）——`compat` 是本插件接管的路由字段，关掉开关却留着旧值等于开关没生效。只写路由级不写模型级（宿主里模型级优先，会与用户逐模型取值打架），且只发 `api === 'openai-completions'` 的路由。
- **`excludes` 是"零操作排除"而非"撤销"**：命中者在 provider 循环入口整条跳过，填充 / compat / `force` 全不作用；已写入值原地保留——插件无字段来源记录，分不清插件写的与用户手写的，"清除"必然误删。瓦片释义与 README 须写明"仅对保存之后的行为生效"，正确顺序是**先加排除、再建提供方**。记忆清理**不豁免**排除项：跳过处单独循环其模型做同样的重建，但不产生对该提供方的任何写回。
- **必须允许填入不存在的 id**，故不做候选约束控件；UI 用「命中」表达"当前确有同名提供方、排除正在生效"，未命中是普通样式、**不得画成错误色**（0 命中也常驻）。命中判据取 `llm-pi-ai` user 层的 `providers` 键——与 `fix` 遍历同一份数据，零漂移。
- **不自动清理失效 id**（顺手 prune 会清空用户列表）：列表顺序是录入意图，脏检测用顺序敏感的逐位比较。去重分两层——录入端当场拒绝写入；`selfHealConfig` 兜住手改配置文件，仅当 `Set` 收窄后**变短**才产出 op。`fix` 的写回不碰自有 NS 的配置键，`efforts` 重建是唯一例外。
- **图片模态只缓存正向信息**（纯文本省略以控体积；`pdf`/`video`/`audio` 忽略）。**容量哨兵**：`99999999` 与 0 一律视为无该字段（写 0 会被宿主 schema 拒绝并连累整批）。
- **id 匹配宁可漏不错配**：精确 → 词干 → 前缀三级，词干 / 前缀多命中即判无命中。词干拆为 `{base, digits}`，digits 取所有日期式数字组剥除连字符后的拼接，仅当两边都有 digits 才比对；任一边无 digits 则退回 base 兜底。
- **`efforts` 是运行时记忆而非用户配置**：嵌套对象（model-id 可能含 `/`，拼接无法还原）、宽松解析（坏结构回落 `{}`，不判整段快照非法以免连累自愈重写）、`isDirty` 不比较它；卡片「保存」写整段快照时 `efforts` 取**写入当刻的实时值**（卡片不拥有该字段，用草稿副本会覆盖"开卡后切过模型"的那段记忆）。
- **Node 半只负责记忆的持久化、解析与失效清理，不自动设置级别**（后端写配置只影响新会话）——自动恢复与自动设 `high` 必须走前端 `directory.select`，且自动设置不写记忆（经 `pendingAutoSet` 守卫跳过反向触发的投影变化）。
- **`rememberEfforts` 关闭只停止"保存新的"**（effort-change 分支跳过），"恢复"照常取真实记忆；是否清空由卡片在开关由开转关时**立即**确认（经 settings scope 直写；"有记忆"判据取实时值，清空失败显式报错，避免开关已关而记忆未清无从察觉）。
- **`defaultHigh` 三条护栏**：记忆优先（有记忆即跳过，即便因不受支持而未恢复）、不覆盖既有级别、不干预同模型改级别（含手动选「provider default」）。它与 `rememberEfforts` 同属「用户体验」瓦片的同一条监听链，两个开关都**不读 `excludes`**。
- **重置推理级别不写配置段、不改开关**（关掉开关等于修改配置，用户不一定要）：只剔除 `reasoningEfforts`，容量 / 输出上限 / 图片模态与自定义字段保留。竞态防护靠 Node 半模块级守卫而非前端（置位先于 mutate 同步完成，覆盖写回同步派发的事件），`forceUpdate` 端点同样被守卫拒绝。
- **恢复备份只回退交集**（备份与当前都存在的 provider 内的 model）：被删的 provider / model 不复活（复活后 api-key 已随 provider 删除，等于看得见用不了），启动后新增的原样保留；备份是 model **整对象**快照，故用户手写的同名键一起回退。备份只在 `apply` 最顶部捕获一次、仅存内存，**绝不做延迟补捕**——晚于写回捕到的是被填充过的内容，比没有更危险。备份缺失或当前无 `providers` 段要**显式抛错**（回 0 会显示成「已恢复 0 个模型」，与"确实无可恢复"无法区分）。
- **验证是只读诊断、只由用户主动发起**：不随填充后台自动验证（`fix` 是事件热路径且每次重试重读 revision，掺入网络 I/O 会让 `SETTINGS_CONFLICT` 反复重算重验；「已验证」账本还须新增顶层配置组并升级，且凭据/模型一变即过期）。结果**即用即弃**：不写 settings、不占事件流守卫、不与三个写回端点互斥、也不进配置键；列表**不套用 `excludes`**（排除只约束对配置的写入）。
- **验证只判「适配器是否开始产出内容块」，不判内容**：提示词仅 `Just say OK`，收到首个 `block-start` 块即判成功并立即中断（省额度）；只看返回文本会把不按提示词作答但实际可用的模型误判为不可用。**不可写成「首个非 `finish` 块」**——`usage` 块不含受理信息，额度耗尽的 key 实测也会先来一条，那会把用不了的 key 判成可用（宿主 `isVisibleChunk` 同样把 `usage` / `finish` 排除在「内容」之外）。全程无内容块、`error` / `aborted` 终止、异常与超时一律判不可用。档位 id 取 `reasoningEfforts` 的键（即模型页送出的同一个值），候选列表与档位探测顺序按 `EFFORT_LEVELS`（`off < minimal < low < medium < high < xhigh < max`）排序。
- **失败分类只认 `code`，全程不比对文案；短路只有一条判据、分两级**：宿主 `HarnessError.code` 明令「route on this, never by parsing `message`」，故一律不比对报错文案。**`status` 一律不看**：pi-ai 侧抛错只给 `new LlmError(message, code)`、终止错误也只给 `{ message, code }`，任何上游状态码（400、5xx）在到达我们之前就被压成文案（`classifyPiAiError` 正是跑正则从文案里认 code）。据此分类：档位不被支持（`UNSUPPORTED_REASONING_EFFORT`，宿主在派发前本地拒绝，请求根本没发出去）/ 额度耗尽（`QUOTA`、`ACCOUNT_QUOTA`——后者是宿主 error.js 给「账户余额不足」定的字面量，早先误写成 `ACCOUNT_QUOTA_EXCEEDED`，永不命中；额度可能只覆盖其中某个模型，故只压该模型、不压整组）/ 凭据无效（`INVALID_CREDENTIAL`、`MISSING_CREDENTIAL`）/ 端点不可达（**只认传输层失败码 `TRANSPORT` / `STREAM_CLOSED`**）/ 限流与超时（`RATE_LIMIT`、`TIMEOUT`，**单列为瞬态**：它们只否定这一次，既不算不可用、也不短该模型的后续档位——实测 429 挡掉的档位隔一会儿就通，判死会把好档位误送进剔除清单；判定依据是宿主 retry-policy 的 `DEFAULT_RETRYABLE_CODES` 里除传输层与 `EMPTY_RESPONSE` 外的那几个）/ 其它。**「`status` 缺失即不可达」是错的**——实测踩过：上游一次 400 因文案里没字面出现 `400`/`invalid_request`，宿主给的是未识别码，于是掉进那条兜底被误判成断线，provider 剩下的模型全被跳过。`EMPTY_RESPONSE`（成功抵达却零内容块）同样归「其它」，它本就不是失败。在此之上另有一级**模型级**短路，判据与 provider 级同源，只剩一条：**能断定后续请求必然失败才短**。档位请求上只有额度耗尽够格（同一把 key 对这个模型的额度已见底，换多少档都是同样结果），只有换模型才可能不同，故只压该模型自己的档位、不牵连同组其余模型。其余一律不短，宁可多烧几次额度也不误杀：上游 5xx 与其它厂商侧拒绝多半是服务端的一次性故障，换个档位可能就通；限流与超时只否定了这一次；「档位不支持」恰是唯一值得继续逐档位验的结论。只对带失败事实的探测生效：正常终止却没有内容块属退化完成而非报错，换档位仍可能出内容。
  - **「探测」是不带 `reasoningEffort` 的对照请求，由浏览器半声明要不要发，它不是被验对象**：本插件的「不支持」信号来自上游 4xx，而 4xx 在上游那里是 invalid_request 的统称，按 `code` 分不出「档位不支持」与「参数写错」。探测提供对照——不带档位都跑不通的模型，换任何档位也是同样结果，没必要把每个档位各烧一次；跑得通的模型再逐档位验，失败才可能归因到档位。**是否需要探测由计划里每个模型的 `needTest` 声明，Node 半不替浏览器半反推**：关掉档位开关时全部请求本就不带参数、模型压根没声明档位时也没有档位可比——这两种情形下那一次不带档位的请求**本身就是被验对象**，再补一条纯属白烧额度（无档位却声明要探测按非法入参拒绝）。探测**不进计划、不进明细、不计任何统计**，跑通时也不发进度帧：故记录里每一条都是被验的那一次，帧上的「还剩几条没验」也与实际待验条数对得上。**唯一的例外是探测失败并据此短路**——那个模型一条都没验成，不发记录它就在记录区彻底消失，用户只看到别的模型的结果，无从知道它为什么没出现；故此时发一条**不带档位的模型级记录**（撞上端点不通 / 凭据无效则发提供方级），`skipped` 含探测自身——它同样没发出去。它只参与两件事——当档位结论的对照，以及在撞上端点不通 / 凭据无效时如实反映到该组的 `reachable` / `keyValid`（它也是真发出去的一次请求，不许当它没发生过）。为免「计划里没有它、计数却涨了它」，上限按**真正发出的请求数**（档位数 + 探测数）计。
  - **判「档位不支持」的两个条件**：探测已通过 + 该档位被判为**参数不正确**（`INVALID_REQUEST`）。第二个条件取的是宿主 `classifyPiAiError` 已经从文案里归一好的结论——**我们不再自己比对任何文案**。试过更严的「再要求原文含带引号的档位值」，实测两头都不讨好：有的上游压根不回显档位名（只列可用档位），判不出来；而有些网关在 4xx 里回显请求体，按文案匹配只会把「上下文超限」这类失败误判成「这一档被拒」，进而送进剔除清单——判错一次的代价是用户删掉一个其实可用的档位。控制变量法已经足够：基线（不带档位）通过了，说明端点、凭据、额度、网络、模型名全部无碍，两次请求唯一的变量就是档位。
  **同一提供方共用同一 url 与同一把 key**，故「端点不可达 / 凭据无效」一旦出现，该组剩余请求必然同样失败，立即短路——省下的额度就是省下的钱。**唯一追加的 provider 级是「本组首个请求就超时」**：成因在请求之外（url 不可达、端点服务中断、本地网络不通），后面几十条请求只会是同样无意义的超时；理由记 `timeout` 而**不是** `unreachable`——超时不是传输层失败的证据，把「可达」翻假会让用户以为端点已确认连不上。首个之后的超时不同，那时链路已经跑通过，只是这一次慢。额度耗尽只压当前模型（它多半是**按模型**设的，有的厂商给某个模型单独限额），**既不压整组也不否凭据**：`keyValid` 说的是整把 key 有没有效，拿一个模型的额度去否定它是层级错配，要看出什么事得看该模型自己的明细条目。档位不被支持属逐模型逐档位的个体结论，只记录不短路；其它厂商侧拒绝（如该模型不存在）同理。**我方超时不算端点不可达**（首个那条除外）：慢端点不该被当成断线，它与限流同归瞬态，如实记进明细，但不据此判不可用、也不短该模型的后续档位；抛出的异常归入「其它」——宁可不短路，不可误短路。
  曾考虑「每提供方先发两个预检请求」（假模型探可达性、假档位探报错文案并缓存比对），已否决：预检并无必要（首个探测的失败事实已含全部信息）；假档位会被宿主本地校验拦下、根本发不出网络，探不到端点行为；缓存报错文案与「禁止比对 message」直接冲突；且会让「提供方正常」这一常见路径白花两发。
- **验证结果同时给明细与统计**：统计（逐提供方的可达 / 凭据 / 可用数 / 是否短路，加全局计数）供一眼看完；**明细 `results` 逐条给出「提供方 / 模型 / 档位 / 结论 / 失败原始事实」**，供后续拿明细做操作（只重验某个提供方、只补验某些档位、按 `code` 细分失败原因等）。明细只含**实际发出**的被验请求——探测不是被验对象，不在其中（它对档位结论的作用在明细之外体现）；被短路掉的从未发出去、没有结论可言；哪几条没跑由逐提供方的 `planned` 与 `probed` 之差给出（短路以整组为单位，按组定位即可）。`tested` 取自计划而非明细，故「用户勾了几个」不会因某模型被整体短路而少算。**收尾那行文案随档位开关分两档，数字口径跟着「档位」的含义走**：关档位时请求本就不带参数、没有级别可报，故报「勾选 `tested` 个 / 可用 `models` 个」；开档位时级别分母取 **`plannedEfforts`**（计划里带档位的条目数）而不是 `planned`——`planned` 还含「没声明档位的模型」那一条（它验的是模型），拿它当分母会让「X / Y 个推理级别」凭空多出一个，用户会以为有档位没验成。而档位开关开着却一个级别都没计划时（勾选的模型都没声明档位）退回模型口径：那行只会显示「0 / 0」，比不给结论还糟。`failure` 保留宿主原始 `code` / `status` / `message`：`code` 供调用方做比本插件更细的分类，`message` **仅供展示与诊断**，分类绝不可依赖它。
- **每 provider 单并发、跨 provider 最多 5 路、不做退避重试**：一个 provider 一条串行链（`groupProbesByProvider` 的分组即结构保证），前一次返回才发下一次以规避 429。请求总数封顶 200（逐模型逐档位展开会累积条目，探测也算一次请求，超出即拒绝而非静默截断），单次 30s 超时即判不可用。列表**默认不预选**、关窗即丢弃勾选：验证花真实额度，预选全部等于把「误点即扣费」变成默认路径。分组头另给「全选 / 取消全选」小键——验证某一提供方的全部模型是高频操作，逐条勾选太慢；键的组件、尺寸、文案逐条照官方 `candidateToolbar` 的 ghost 小键，文案判据用 **`every` 而非 `any`**（部分选中时仍显「全选」，全选中才翻成「取消全选」，与官方 `allVisibleCandidatesPicked` 同语义）。该键仍需用户主动点击，不因此改为预选。**文案判据与点击方向必须共用 `groupAllPicked` 这一个纯函数**：两处各写一遍 `every` 一旦不同步，就会出现「文案显示取消全选、点击却是全选」的反直觉行为且不报错。该函数与 `toggleGroupPicks` 一并落在 `client/model.ts`（不留在组件内），与瓦片总控的 `masterValue`/`applyGroup` 同构，因而能被 `test/` 覆盖——选择代数留在组件闭包里就等于没有测试。
- **验证弹层自确认**：候选框内已有 warn 额度提示与 warn 语义验证键（`.dsh-mf-warn`），构成自确认故不再叠二次确认弹层；**卡片 footer 的「验证模型」触发键同样取 warn 语义**——点开即进入要花额度的流程，警示前移到入口比藏进弹层更有效。它是 `.dsh-mf-discard` 叠加 `.dsh-mf-warn`，靠后者 `:not(:disabled)` 的高特异性压过次级描边与字色，聚焦环仍由 `.dsh-mf-discard` 提供。类名不叫 `confirmWarn` 而叫 `warn`：触发键与确认键共用同一套 warn 样式，`confirm` 前缀会误导读者以为只用于确认。footer 内因此有两个 warn 键，靠位置与文案区分。
- **档位开关关掉时是不发 `reasoningEffort` 参数，而不是挑一个最低档位去验**：端点可能有自己的默认推理级别，不带参数验的才是用户实际会走的那条路径，发 `off` 验的是另一条。开关文案「验证推理级别」同时覆盖两态。两种模式下未声明档位的模型都只发一次不带参数的请求——开态对它没有可验的档位，与关态同形。**档位开关与两键并排同一行、开关靠左**：初版把它放在 body 内，照的是宿主 `RiskConfirmation`（敏感操作前置确认原语）的排法——确认控件留在正文内、距上一段 `margin-top:20px`，`.footer` 只放取消/确认两键。弹层加宽到 560px 后那条依据不再成立：正文末尾只剩开关一个控件、底部只有两键，视线要来回跳。故并入 footer 同一行，以 `space-between` 覆盖宿主 `.footer` 的 `flex-end`（开关左、两键右）；**记录区随后也移出 footer**（见下条），footer 只剩取消/确认两键，自绘的纵向容器一并删掉，底部交给宿主 `.footer` 自身的 `flex-end + gap:8px`。纵向间距不再逐处取档位，改为**正文内部一律 12px**：宿主 `.body` 是 `flex column` 但**没有 gap**，段间距全靠各自 margin 给，而 flex 容器里 margin 不折叠 ⇒ 紧挨两段各自的 margin 直接相加（探测弹层「范围提示 ↔ 额度提示」实测 24px 正是 12+12）；逐处核算叠加关系既易错又难改，故两个弹层的正文各套一层自绘容器 `.dsh-mf-verifyBody`（`flex column + gap:12px`；验证弹层里它是「额度提示 → 选项卡条 → 当前面板」三段相邻，未选中的面板带 `hidden` 即 `display:none`、不是 flex 项，换页后不留空段）把节奏收在一处、各段自身 margin 归零——容器内任何两段的净距恒为 12px，末段归零后「正文 ↔ footer」只剩宿主 `.dialog` 的 `gap:20px`，与「描述 ↔ 正文」的 20px 相等，不必自造数值。12px 取自 `ModelsSection` 的 `.section` gap（小节内相邻块那一档，同款官方 `.notice` 正是该容器的直接子元素）。**列表项间距用默认（不写 gap，即 0）**，行内纵向内边距仍逐条取官方 `candidateLabel` 的 `6px 8px`，相邻两行靠这层内边距自然分开；原先照抄官方 `.candidateList` 的 2px 是「同屏尽量多列模型」的紧凑档，这里不取。行内元素（键与图标、开关与其释义键）仍取官方 8px / 6px，不受这条影响。**卡片里动作键行与瓦片的距离回到 12px**：`.dsh-mf-bar` 自带 `padding:12px 0 0`，与 `.dsh-mf-body` 的 `gap:12px` 叠加成 24px（早于本轮布局调整就存在，非布局调整引入）；父级 gap 已给出 12px，故删掉这条 padding，两处 12px 不再叠加。在途期间弹层原地转圈（宿主 `StateDot` 的 `ongoing` 态即转圈本体，置于确认键内部作首个子节点——宿主 Button 自身是 `inline-flex` + `gap`，零额外 CSS），跑完不关窗，结论追加成记录区末行、**不再往卡片状态行渗透**，由用户看完自行关窗——结论此刻就在用户眼前，再抄一份到关窗后才可见的地方只是把信息挪到视线之外；除验证外的操作结果才一律走卡片内联状态行——逐条冒出来的记录只交代过程、不交代「总共怎么样」，否则用户只能自己数末行才知道结论。在途的确认键文案改为「停止」而不再保持不变：弹层自此有了出口，键不变会让用户只能干等（取消键仍按原样在途中禁用，取缔的是「无路可走」而非「关窗 = 停止」这层意思）。
- **验证弹层的记录区单列为一个选项卡，与模型列表并列**：记录是「正在发生的事」，模型列表是「挑哪些模型去验」，同处一屏只会互相挤——跑起来时正文被记录区顶开、勾选区被推出视野。故正文顶层改为两个选项卡（模型列表 / 验证记录），额度提示提到选项卡条之上、两个面板之外（它讲的是「这轮会做什么」，对两页都成立，不该只归其中一页）。**点「验证」即切到记录页**：进度只落在那一页，发跑后不该先在列表上白找一趟。**每次开窗回「模型列表」**：关窗已丢弃上一轮的勾选与记录，落在空记录页只会让人以为记录还在。**两个面板都常驻挂载、切页只改 `hidden`**（与官方那份 `visitedIds` 同一用意）：记录区的 `TerminalBlock` 自带展开 / 收起状态，卸载即丢；还没发起过（`total === 0`）时记录页给一行空态而非空白面板。条与面板的 `role` / `aria-selected` / `aria-controls` / `data-active` / 未选中 `tabIndex:-1` / 方向键循环与 Home / End 后移焦，以及选项卡条的样式数值，逐条复刻官方「设置 → 内置插件」的插件视图选项卡（`PluginsSettingsSection`）——宿主没导出同款原语，故本地自绘；唯面板上方的留白不取官方的 `padding-top:2px`——本项目的正文一律 12px 更优先，选项卡条与面板是相邻两段、那 12px 由正文容器的 gap 给（未选中的面板带 `hidden` 即 `display:none`、不是 flex 项，换页后不留空段）；不取 `SegmentedTabs`，那是分段控件、形态不同。原「两个弹层的记录区一律排在提示段之下、开关之上」那条就此只对探测弹层成立（其序为「范围提示 → 额度提示 → 记录区 → 两个开关」）。
- **进度走 SSE 流而非轮询，官方安装那条通道第三方不可用**：验证可能跑数分钟，UI 只能转圈等于让用户猜是不是卡死。宿主装插件时的实时输出来自 **pnpm 子进程 stdout → Cordis 事件 `plugin-manager/install-log` → WebSocket 多路复用**，但事件转发走的是 `api/remotes/src/remote-events.ts` 里一份**编译期常量白名单**（27 条），第三方事件永远不会被派发；`@Remote({ mode: 'stream' })` 虽 Host 侧可发现，客户端却要求 Typert 编译器产出的 strict codec，且挂载清单同样是硬编码——**第三方挂 stream Remote 没有先例**，为一次诊断进度引入整套代码生成，风险收益不成立。改走 `connection.fetch.register` 的 exact 路由：`new Response(ReadableStream)` 是官方 `session-log-export` 正在跑的同型用法，且白拿信任围栏、浏览器认证与「客户端断开 → `request.signal`」（`http-bridge.ts` 把 abort 挂在 `res` 的 `close` 而非 `req`——Node 16+ 的 `req.close` 会在请求体读完就触发，把刚开的流掐掉）。内容类型取 `text/event-stream` 虽不写 SSE 客户端，却能绕开 gzip 中间件——它**显式跳过**该类型（`host/webserver/src/index.ts`），普通类型一旦被压缩缓冲，流式就没了。浏览器侧用 `fetch` + `getReader()` 而非 `EventSource`：后者自动重连，而重连等于重跑整轮验证。
- **关窗 / 断连 / 点停止一律中止，不再有「无人收割」的窗口**：原注释担心「提前关窗会留下无人收割的一批请求」，那是请求-响应式时代的真问题——响应回不来，服务端那批探测就白跑到底，用户一走，钱照烧。流式之后连接的生命周期**就是**这次验证的生命周期，断开即中止，Node 半据此让执行循环早停（只断在途请求而继续循环，后续探测会带着已中止的信号跑出一串假失败）。因此弹层的遮罩 / Escape / × 与「停止」键全都汇入同一个 `AbortController`。**中止不发 `done` 帧**：消费方见「流自然结束却没等到 done」即知这轮没跑完，据此保留进度而不是报成功。被中止时弹层不关、已打出的行留着，主键复原可重跑（重跑会清空记录，免得上一轮的残留行混进这一轮）；记录区的 settle 文案也因此从宿主原语的「已完成」改成「已停止」——用户主动停止不是失败，不该落 `error` 态。**「停止」按下即在记录区追加一行「已停止，本轮不再继续…」**：它是唯一不关窗的中止方式——遮罩 / Escape / × / 「关闭」键那几种的记录都随弹窗一起丢掉了，只有它留下的进度用户还看得见；中止这件事该落在日志里，而不只是那个「改了就改了」的 `done` 状态标签（标签只有两个字，说不清是本轮到此为止还是仍会继续）。两个弹层同一处理，措辞刻意只说「不再继续」、不说「已还原」——后者是探测式填充中止后的事实（那轮整轮还原），而验证是只读诊断、压根不改任何东西，写上去反而不准。
- **wire 只发结构化帧，文案与格式化全在浏览器半**：locale 只存在于浏览器半（`src/client/locale-zh.ts` 与 `locale-en.ts`），文案归 Node 半就等于把本地化绑死在 Node 产物上，改语言要重发 Node 半。故进度帧是判别联合（`opened` / `probed` / `done`），显示词与行模板（`{provider}: {model} [{effort}]：{result}`，层级用冒号而非斜杠——模型 id 自身就含斜杠，如 `z-ai/glm-5`，拿它当分隔符读不出层级）由浏览器半拼。`probed.skipped` 只在触发 provider 级短路时出现，值是该组剩余未发出的条数——消费方才好交代「这组还剩几条没验」。`decodeProgressFrame` 逐字段校验而非 `JSON.parse` 了事：`done.summary` 直接驱动卡片上的统计数字，形状不对却当成合法帧用，等于把 `undefined` 当 0 展示。provider 级失败行不带模型与档位（那不是某个模型的问题，是整组都不成立），非 provider 级才补档位词。
- **剔除不被支持的档位走 Node 半（守卫不可省）**：初版放在浏览器半直写 settings，被否——那条写回会被本插件的事件链当成「配置变了」而触发 `fix`，把刚剔掉的档位从 models.dev 又填回来，用户点了剔除却什么都没变。守卫（`src/guard.ts`）是 Node 半的模块级标志，浏览器半跨不过半纯度门禁，故这条写回也必须在 Node 半：经 `queueTask` 写回、与其他三个写回端点以守卫互斥、revision 冲突重试。确认框照「清空推理级别记忆」那层二次确认，两键文案换成「剔除」。
  - **不支持档位明细由 Node 半直接给出**（`VerifySummary.unsupportedEfforts`）：统计值前端直接用，不必自己从 `results` 里重算；而剔除要写配置就得逐条定位，那块不聚合只给明细——两处各筛一遍，口径一旦分叉就会漏剔或多剔。
  - **只认「明确判为不支持」**：超时、限流、额度耗尽、端点不可达都只是**没验成**，不是不支持，拿它们去删用户填的配置就是误伤。`pruned` 只计真正从现有档位表里剔掉的条数——确认框里的 `n` 与结果里的 `x` 可能不等，那是如实而非出错。**剔除结果一律照实显示条数、为 0 也不例外**（单一 `pruneDone` 文案，不另设「无须剔除」分支）：目标在剔除期间已被用户改掉、或其提供方正落在排除列表里时（`planPruneEfforts` 整组跳过，且不撤销已写入的内容），0 就是真实结果。**剔除结束后关闭弹层**：结果写在卡片状态行上，不关窗用户根本看不到。
  - **幂等**：目标里那些当前已不在档位表中的（验明确认之后用户自己改过）一律不命中，零写入也不虚报。
  - **尊重 `excludes`**：排除语义对本插件的写入处处生效，不因这次由用户发起而破例（`verifyCandidatesOf` 当初不套 excludes，正是因为验证只读、写入才受限）。
  - **档位被剔空时在写入前就判定**，让整个 `reasoningEfforts` 键不出现在新值里，而不是先写空再删的两次写入：路径 op 不支持数组下标中间段，只能整段 `set`，而空壳留着会反复触发写入判定。
  - **自动填充不会把结果翻回去**：用户手填的档位被填回是正常的（models.dev 说它该在那儿）；模型页上已有推理级别的模型本就跳过填充；真被剔到零的只可能是全手填的模型，剔空后该字段整个消失，模型回到「未声明档位」态，此后也不会被填充。
- **探测式填充（逐档试出可用的推理级别并立即补全）**：与验证同一条 `connection.fetch` 流、同一个执行引擎（共用的一半按职责分四层：`src/probe-verdict.ts` 收失败分类与两级短路判据，`src/probe-plan.ts` 收入参校验与计划展开、按提供方分组与两条硬闸配额，`src/probe-engine.ts` 收单次请求与受理判据与并发编排与进度帧，`src/probe-report.ts` 收逐组汇报与全局汇总；两者只差「一组里怎么逐条跑」这个 `runGroup`），差异只有下面几条。
  - **必须先把候选档位临时预声明进配置，探测才有意义**：宿主在派发前按**模型配置里声明的档位**本地校验（`resolveCallWithInfo`，见 `docs/host-api.md`），未声明的档位不出网、只本地抛 `UNSUPPORTED_REASONING_EFFORT`。所以「探测一个没声明档位的模型支持哪几档」在配置不动的前提下根本无从谈起——七档全被本地拒。预声明是本功能的必要前置而非副作用：它在同一轮结束时被收敛写回收回，且增删统计以**预声明之前**的档位表为基线，临时档位既不计新增也不计删除。
  - **收敛写回在流内完成，终帧最后发**：`VerifySummary.fill`（模型数 / 新增 / 删除）是探测式填充专有字段，验证恒缺省。之所以不另开一个 `fillEfforts` 写回端点，是因为收敛要用到「预声明之前的那份档位表」，那份状态只在 Node 半这一轮里；拆成两个调用就得让浏览器半把它自己看到的旧表回传，而浏览器半的快照可能已经过期（用户在探测期间改过配置），据此写回会把用户刚改的档位翻回去。
  - **两级短路的判据与验证同源，只剩一条「能断定后续必然失败才短」**：provider 级是 `providerBlockReason(outcome, firstRequest)`（端点不通 / 凭据无效 / 本组首个请求超时），模型级是 `shouldSkipModelTail(outcome, failure)`——档位请求上只有额度耗尽够格，故**额度耗尽在两个功能里都只短到该模型自己的档位尾**：同一把 key 对这个模型的额度已见底，换多少档、换哪个模型都是同样结果，继续逐档试纯属烧额度和时间，用户要的「这一档行不行」在第一次就已经没有答案了。上游 5xx、其它厂商侧拒绝、限流、超时一律不短（多半是一次性故障，或只否定了这一次），宁可多烧几次额度也不误杀可用档位。本功能没有基线探测，故「其它厂商侧拒绝」落在档位请求上时**不再**构成模型级短路——那是验证侧 `shouldSkipModelTailAfterBaseline` 才认的，那里的请求压根不带档位。被短路的模型按下面「没跑满即还原」处理，本功能不必新增任何收敛逻辑。
   - **不搬验证的「每模型额外一次基线探测」**：本功能的对照比基线更紧——更低档跑通 ⇒ 端点、凭据、额度、网络、模型名都无碍，唯一的变量就是这一档，而代价为零；基线唯一多换来的是「`off` 自己也能被判不支持」，而 `off` 被拒不判不支持并不影响补全（其余六档照补、照记），却要让每个模型多烧一次请求（7 → 8，而本功能正是额度开销最大的那个）。
  - **判「这一档不支持」的第二条件换成「同模型已有更低档跑通」**：验证有专门的基线请求，本功能的基线就是预声明 + 已跑通的更低档（更低的档已通 ⇒ 端点、凭据、额度、网络、模型名都无碍，唯一剩下的变量就是这一档）。第一档就被判 `INVALID_REQUEST` 时第二条件不成立，只记「其它」——那更可能是模型本身的问题，判成档位不支持会把一个其实能用的档位误判掉。
  - **两种收敛口径都由「剔除不支持」开关选**：关 = `可用 ∪ 原有`（只增不减），开 = `可用 ∪ (原有 − 明确判不支持)`。两条都只认明确状态：限流、超时、额度耗尽、端点不可达都只是「没验成」，既不算可用也不算不支持，拿它们去动用户配置就是误伤。档位表算空即整个 `reasoningEfforts` 键删掉（回到未声明态），与剔除路径同一形态。
  - **「剔除不支持」只对「探测所有」有效**：走「探测未填充」的模型本来就没声明过档位，判不支持的那几档压根不会写进去，无从剔起；那一轮里浏览器半直接按「关」下发并在途禁掉开关，避免留一个亮着却不生效的开关骗人。
  - **没跑满结论的一律还原，中止则整轮还原**：某模型的请求没拿满（被 provider 级或模型级短路连带）就**不动它的档位表**，直接还原成预声明之前的样子。本轮被中止时更进一步——**整轮**还原，连已跑满七档的模型也不补、不剔：用户按「停止」要的是原样停下，不是「探到一半、填一半」。半截结论不足以动用户配置，而「探到多少补多少」的结果既不可预期、也可能把半截结论写成定论。
  - **「忽略排除」同时作用于探测范围与两次写回**：这是本插件里唯一一处突破「排除语义对写入处处生效」的地方，故做成显式开关而非隐式例外；两边必须共用同一个值，只在一边放开要么白探测一轮、要么探测范围与写回范围对不上。附带后果：兜底备份要写进自有段，故忽略排除时自有段读不到也不再是「不算失败」，而是**整轮中止**——没有退路就不动用户配置。
   - **开跑前把整段 providers 压一份兜底备份，启动末尾见键即回退**：崩在中途时进程已经没了，收敛没有机会跑，预声明就留在用户配置里，而插件也不知道该收敛成什么样，落盘的那份是唯一退路。备**整段**而非探测范围——预声明动了范围外的模型时崩掉，只备范围就无人回收；反过来按整段覆盖又会抹掉用户在探测期间对范围外模型的正当编辑，故回退复用「恢复备份」的 `planRestore` 交集语义（只回退共有提供方的共有模型）。压成 deflateRaw + base64 的字符串放自有段顶层键 `probeBackup`：大配置可达数百 KB，常驻不合适；顶层键不进版本快照，故**不动 `CONFIG_VERSION`**。存不下即整轮中止。位置在启动链末尾、首轮 `fix` 之后（迁移与填充在前），回退后再补一轮 `fix`，否则被撤掉预声明的模型会停在未填充态、主功能失效。解不出内容即丢弃且不回退；**恢复成功才清备份**，防止恢复本身失败时退路先没了。
   - **清备份放在收敛落盘之后的最后一步**：唯一残留窗口是「收敛已落盘、备份还没清」时被杀，下次启动会把这一轮**已成功**的补全一并回退（多探一遍即可重来）；反过来先清后备着，崩在收敛之前就无人回收预声明，把用户配置留在半截状态，更糟。清不掉只告警，不把已成功的补全报成失败。
   - **中止恢复走内存基线，不复用那份落盘备份**：中止时进程还在，`declareProbeEfforts` 返回的 `preexisting`（预声明之前每个模型的档位表，无档位记空表）足以把本轮动过的 `reasoningEfforts` 原样写回，粒度更细、零落盘零解压；若改走备份，就得连没碰过的模型和字段一并按备份覆盖，误伤面反而更大。两类故障的交汇处是有覆盖的：中止后收敛写回本身失败抛错时清备份不会执行，备份留在段里，下次启动幂等回退。
  - **事件流守卫持有整轮**（预声明 → 探测 → 收敛之间不放开）：放开的话，用户或别的插件在这几分钟里改一次配置就会触发 `fix`，把预声明按 models.dev 改回去，探测剩余的请求会被宿主本地拒绝、结论全错。代价是一轮探测期间其它写回端点被拒、自动填充暂停——一轮探测本就是用户主动发起的，且带着未收敛的写回，放开守卫的风险比让出这段时间更大。探测流入口也因此先查守卫，与写回端点互斥。
  - **收尾延迟 2.5s 再关窗**：补全写回很快，跑完立刻关窗的话用户还没看清记录区弹层就消失了，结论等于没给。故先把汇总与补全结果追加进记录区、再提示即将关闭，定时器挂 ref 以便关窗 / 卸载时撤掉（否则用户已经走了回调还会再改一次弹层状态）。时长取「读完一句结论」的量级，不做配置项：更久用户自己会关，更短来不及读。
  - **配额按模型数封顶 200（至多 1400 次最小请求），超出整体拒绝**：沿用验证「不静默截断」的纪律——截断会让用户以为「全查过了」。与验证的 200 次请求上限是同一个量级的东西，故两条硬闸写进同一个 `planProbes` 的 `ProbeLimits`。
- **RPC channel 由本插件在已注入 webServer 的子 fiber 上自注册**，不用宿主 `connection.rpc.handle`（后者在服务自己的 ctx 上求值 `owner.webServer`，而 connection 已不再注入它，必然抛错）；复用宿主 `requestRejection` 做信任围栏、按宿主 `rpcFetchHandler` 复刻信封与状态码。
- **卡片按钮取「保存」不取「应用」**：写 settings 即前端职责终点，填充由后端触发、填了几条前端无法感知。**瓦片默认收起、同时只展开一个**（官方手风琴语义）；`defaultOpen` 同时决定保存成功后是否自动收起——默认收起才自动收起（模型页 footer 席），默认展开的三席保持展开。**「取消」键仅未保存时渲染**。
- **瓦片总控开关按 `every` 显示**：组内全开才显示开，部分选中显示关，点击即整组补全为开。早期用 `any`（任一为开即开）有两个问题——部分选中显示成「开」会误导，且点击会把用户已勾的那几行**抹掉**（他本意是补全）。口径与验证弹层的分组「全选」统一。代价：从部分选中到整组全关需点两次（先全开再全关）。总开关本身无存储，只是个批量操作；`compat` 组只有一行，`every` 与 `any` 等价，不受影响。
- **卡片末尾固定一条版权 / 联系行**（分割线 + 地址 / 版本 + 两个跳转键），三元素同款、不做主次层级；「问题反馈」指向 `/issues/new?body=` 预填「标准 issue 模板 + 插件版本」，占位符用 `--要填什么--`。**卡片底部自上而下三段**：动作键行（强制更新 / 重置推理级别 / 恢复备份 / 验证模型，靠左起排、组内可换行、**位于分隔线之上**——键数增长后不再与取消/保存相互挤压）、分隔线 + 取消/保存（靠右 `flex-end`）、分隔线 + 联系行。动作键行刻意不设分割线：它承接上方瓦片，分隔线只用来分开「卡片正文」与「页脚操作/信息」。`.dsh-mf-actions` 是三处键组共用的容器，故换行能力加在它身上而非逐行另设。
- **不引入 `failed` 态、不做「恢复默认」**：三组布尔恒合法、写入为单字段原子写，失败时 `dirty` 已传达该信息；官方 reset 依赖字段级 user/base 分层与"未填回落"语义，本插件是整体显式快照。
- **对外报告状态的文案一律以句号收尾**：状态行是卡片上唯一承载「刚才那次操作结果」的位置，同一位置时而句号收尾时而戛然而止，读起来像两种语气。范围是全部对外报告状态的行——`setNotice` 的十二个结果键（`saveDone` / `forceDone` / `forceNone` / `forceFailed` / `resetDone` / `resetFailed` / `restoreDone` / `restoreFailed` / `pruneDone` / `pruneFailed` / `clearEffortsDone` / `clearEffortsFailed`）、`role="status"` 的加载与只读两行、字段级 `role="alert"` 的排除 id 报错，以及宿主服务缺失时卡头那行 `unavailable`——中英文案同改。**两类文案不在此列**：加载中的省略号本身即行尾标点；验证记录区的逐条结果（`provider: model [effort]：可用`）与「已跳过 N 项」是数据条目而非句子，加句号反而不成体例。
